# [HU-001]: Jarvis Mode - Conectar repositorios a un proyecto

## 1. CONTEXTO
| **Módulo:** Integraciones / Repositorios |
| :--- |

### **Como** usuaria de Orquestrador 360 **Quiero** asociar uno o varios repositorios (GitHub o Bitbucket) a un proyecto usando un Auth Profile ya configurado **Para** que Jarvis lea señales reales de trabajo sin que yo las reporte a mano.

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. Desde el drill-down "Detalle de Proyecto" → sección "Repositorios asociados", botón
   **"+ Conectar repo"**.
2. Selector de **Auth Profile** existente (no un login nuevo cada vez) — muestra los perfiles ya
   guardados con su cuenta y alcance (ej. `mariana@imagineapps.co — org Bitbucket ImagineApps`).
   Si no hay ninguno, redirige a crear uno primero (`[Pendiente: Definir en Tech Ref]` flujo exacto
   de creación de Auth Profile — depende de la investigación de SSO de Google, ver §11 del spec).
3. Al elegir un perfil, se lista automáticamente los repos accesibles con ese perfil — la usuaria
   selecciona uno o varios, checkbox múltiple.
4. Por cada repo seleccionado, un campo obligatorio **Ambiente** (`prod` | `develop`) — sin
   default, la usuaria debe elegirlo explícitamente.
5. Confirmar → el sistema dispara la validación de acceso (2.2) y, si pasa, guarda y arranca el
   digest histórico de 7 días.
6. Mientras corre el digest histórico, la card del repo en la UI muestra estado "Sincronizando…";
   al terminar, cambia a "Sincronizado" con fecha/hora.

### 2.2. Casos de Uso y Reglas de Negocio
- Un proyecto admite **N repos** de distintos providers simultáneamente (ej. 1 repo GitHub + 2
  repos Bitbucket en el mismo proyecto).
- Antes de guardar la conexión, el sistema valida que el Auth Profile elegido tiene **permiso de
  lectura real** sobre ese repo específico (llamada de verificación a la API del provider) — no
  se guarda una conexión "a ciegas".
- `POST /projects/:id/repositories` persiste `{provider, owner, repo, defaultBranch,
  authProfileId, environment, connectedAt}` en `project.repositories[]`.
- `DELETE /projects/:id/repositories/:repoId` desconecta el repo **sin borrar** el historial ya
  ingerido al Project Brain (decisiones/alertas ya generadas se mantienen, marcadas con el repo
  origen aunque este ya no esté conectado).
- El primer digest histórico cubre los **últimos 7 días** de actividad — no se espera al primer
  ciclo programado (§HU-003) para tener información inicial.

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| El Auth Profile no tiene permiso de lectura sobre el repo elegido | "Este perfil no tiene acceso a `[owner/repo]`. Verifica el permiso en [provider] o elige otro perfil." — no se guarda la conexión. |
| El repo ya está conectado a este mismo proyecto | "Este repositorio ya está conectado a este proyecto." — bloquea duplicado, no crea una segunda entrada. |
| No se seleccionó Ambiente (prod/develop) | Botón "Confirmar" deshabilitado hasta que se elija — no se permite guardar sin ambiente. |
| El digest histórico falla (timeout, rate limit del provider) | La card queda en estado "Error de sincronización" con botón "Reintentar" — la conexión del repo se guarda igual, solo el digest inicial falla y es reintentable. |
| El Auth Profile fue revocado después de conectar el repo | En la siguiente sincronización programada (HU-003), el repo pasa a estado "Reconexión requerida" y genera una alerta en el Project Brain — no falla en silencio. |

# [HU-002]: Jarvis Mode - Ver estado de sincronización de repositorios

## 1. CONTEXTO
| **Módulo:** Integraciones / Repositorios |
| :--- |

### **Como** usuaria **Quiero** ver qué repos están conectados a un proyecto, con qué Auth Profile, en qué ambiente, y cuándo sincronizaron por última vez **Para** confiar en que la información que me da Jarvis está actualizada antes de tomar una decisión con ella.

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. En "Repositorios asociados" del Detalle de Proyecto, cada repo conectado se muestra como una
   card con: `provider` + `owner/repo`, badge de **Ambiente** (prod/develop, con color distinto
   por ambiente), Auth Profile usado, y "Última sincronización: [fecha/hora relativa]".
2. Click en una card → expande el detalle: últimos eventos traídos en la sincronización más
   reciente (commits/PRs), y si hay una reconciliación corrida sobre ese repo, el resumen de gaps.
3. `GET /projects/:id/repositories` devuelve la lista completa con estos campos para consumo del
   frontend.

### 2.2. Casos de Uso y Reglas de Negocio
- "Última sincronización" refleja el trigger real (inicio de sesión o ciclo de 3h, HU-003) — no
  un valor estático de cuando se conectó el repo.
- Si un repo lleva más de 24h sin sincronizar exitosamente (ej. fuera del horario 7am-7pm varios
  días seguidos, o fallando), la card lo señala visualmente distinto ("Sin sincronizar hace
  [N] horas") — no se oculta el atraso.

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| El repo nunca ha sincronizado exitosamente (falló el digest histórico de HU-001) | Card muestra "Nunca sincronizado" en vez de una fecha, con el mismo botón "Reintentar" de HU-001. |
| `GET /projects/:id/repositories` para un proyecto sin repos conectados | Devuelve lista vacía `[]`, la UI muestra el estado vacío invitando a conectar el primero (no un error). |

# [HU-003]: Jarvis Mode - Sincronización programada del Project Brain

## 1. CONTEXTO
| **Módulo:** Project Brain / Backend |
| :--- |

### **Como** usuaria **Quiero** que la actividad de cada repositorio conectado se sincronice al iniciar sesión y cada 3 horas durante mi horario de trabajo (7am–7pm), distinguiendo el ambiente (prod/develop) **Para** que el Project Brain no dependa de que yo pegue actas a mano ni mezcle información de ambientes distintos.

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. Al abrir el Jarvis Chat (inicio de sesión), si ha pasado más de X tiempo desde la última
   sincronización de algún proyecto con repos conectados, se dispara una sincronización en
   segundo plano — no bloquea el chat, la usuaria puede seguir preguntando mientras corre.
2. Entre las 7am y las 7pm, cada 3 horas corre automáticamente sin que la usuaria tenga que estar
   activa en el sistema (job programado, no depende de que el chat esté abierto).
3. Fuera de ese horario (noche, madrugada) no se dispara ninguna sincronización nueva — no hay
   trabajo real que traer y se evita ruido/costo innecesario.
4. Cada corrida etiqueta explícitamente el `environment` del repo que está leyendo — un digest de
   un repo `develop` nunca se mezcla con el de su contraparte `prod`.

### 2.2. Casos de Uso y Reglas de Negocio
- El adaptador de repo (`adapters/github/`, `adapters/bitbucket/`) trae commits/PRs de las últimas
  horas desde la última sincronización exitosa (no siempre "últimas 24h" fijo — se ajusta a la
  ventana real transcurrida, para no perder ni duplicar eventos entre corridas de 3h).
- `POST /brain/ingest-event` recibe el digest con `type: "commit_digest"` y el `environment`
  correspondiente.
- Gabriela resume el digest a `{decisions[], alerts[]}` — **sin actividad → sin entrada nueva**
  (no se genera ruido en el Brain por corridas vacías).
- Si un proyecto tiene repos en ambos ambientes (prod y develop), cada uno se sincroniza y se
  resume por separado — no se combinan en un solo resumen que pierda la distinción.

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| El adaptador de repo falla (rate limit, token vencido) durante una corrida de 3h | Se registra como alerta en el Brain ("No se pudo sincronizar `[repo]` desde `[hora]`: `[motivo]`") — no se reintenta agresivamente, espera al siguiente ciclo de 3h o al próximo inicio de sesión. |
| Dos triggers coinciden (inicio de sesión justo en el minuto del ciclo de 3h) | Se deduplica — una sola sincronización corre, no dos digests duplicados para la misma ventana de tiempo. |
| El repo no tiene actividad en la ventana, pero el job corrió igual | No se crea entrada en el Brain — se registra internamente que la corrida ocurrió (para métricas de uso, §HU-010), pero no como evento de Brain. |

## 3. REFERENCIA VISUAL
> No aplica — este flujo es un job de backend sin interfaz directa; su resultado es visible en
> el Project Brain (Detalle de Proyecto) y en el badge "Última sincronización" de HU-002.

# [HU-004]: Jarvis Mode - Reconciliación código↔spec contra Acceptance Criteria

## 1. CONTEXTO
| **Módulo:** Project Brain / Calidad |
| :--- |

### **Como** usuaria **Quiero** que el sistema reconcilie, Acceptance Criteria por Acceptance Criteria, lo que el backlog declara como hecho contra lo que el repositorio realmente tiene (respaldado por tests reales) **Para** que ninguna HU se dé por completada solo porque alguien lo escribió en un acta o backlog.

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. Dentro del Project Brain (drill-down de Detalle de Proyecto), una sub-sección
   **"Reconciliación"** lista cada Acceptance Criteria evaluado, con un estado: ✅ cumple (con
   link al test que lo verifica), ⚠️ sin test (no se puede verificar todavía), ❌ gap (declarado
   como hecho pero sin evidencia en el repo).
2. Desde el chat, la usuaria puede pedir la reconciliación on-demand: *"revisa si el backlog de
   [proyecto] está alineado con el código"* → dispara la corrida inmediatamente, sin esperar al
   ciclo de HU-003.
3. Un gap (❌) genera **siempre** una alerta visible en el Brain — nunca se diluye ni se omite en
   el resumen general aunque el resto del digest no tenga nada relevante.

### 2.2. Casos de Uso y Reglas de Negocio
- La unidad de reconciliación es el **Acceptance Criterion individual** (`- [ ]` de una HU), no
  una impresión general de toda la HU.
- Input: texto literal de los ACs de cada HU (de `SPEC*.md`/backlog) + estado real del repo
  (archivos existentes) + **tests reales** desarrollados específicamente para verificar ese AC
  (a partir de Fase "Calidad" del modelo de fases, `SPEC_JARVIS.md` §4).
- Output: `gaps[]` con `{huId, acceptanceCriterion, testRef, status}` — `testRef` apunta al test
  concreto que lo verifica, nunca a una inferencia u opinión del Auditor.
- Mientras un AC no tenga un test desarrollado, su estado es explícitamente **"sin test"** — el
  sistema nunca afirma cumplimiento que no puede verificar con un test real.
- Corre: (a) dentro del ciclo programado de HU-003, (b) on-demand desde el chat.
- **Limitación aceptada v1** (documentada, no oculta): trabajo hecho fuera del repo rastreado
  (configuración manual, decisiones de infraestructura) puede marcarse como gap aunque esté bien
  hecho — se declara como limitación conocida, no se intenta resolver en esta versión.

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| Una HU no tiene ningún Acceptance Criteria parseable (formato libre, sin checkboxes) | Se marca la HU completa como "no reconciliable" con motivo explícito — no se inventa un AC que no existe. |
| El repo no tiene ningún test para ningún AC del proyecto (etapa temprana) | Todos los ACs quedan en estado "sin test" — el panel de Reconciliación lo muestra como mayoría amarilla, no se disfraza de "todo bien" ni de "todo mal". |
| La reconciliación on-demand se pide para un proyecto sin repos conectados | El chat responde explícitamente que no hay repo conectado para reconciliar — no inventa un resultado. |

## 3. REFERENCIA VISUAL
> Sub-sección "Reconciliación" dentro del Project Brain, Detalle de Proyecto.

# [HU-005]: Jarvis Mode - Timeline unificado por proyecto

## 1. CONTEXTO
| **Módulo:** Project Brain / Auditoría |
| :--- |

### **Como** usuaria **Quiero** un timeline único por proyecto que combine actas, commits, PRs y eventos de reconciliación **Para** poder auditar de dónde salió cada decisión o alerta que aparece en el Project Brain.

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. Drill-down "Detalle de Proyecto" → pestaña "Timeline de actividad": lista cronológica
   (más reciente primero) de todos los eventos que alimentaron el Brain.
2. Cada entrada del timeline muestra: tipo de evento (acta / commit_digest / reconciliation_gap /
   card de Basecamp), fecha, ambiente (si aplica), y un link directo a la decisión/alerta del
   Brain que generó (si generó alguna).
3. `GET /projects/:id/timeline` devuelve los eventos con paginación — no carga todo el historial
   de una vez si el proyecto lleva mucho tiempo activo.

### 2.2. Casos de Uso y Reglas de Negocio
- El timeline es de **solo lectura** — es la vista de auditoría, no un lugar para crear eventos
  manualmente (eso sigue siendo `POST /brain/ingest-event`).
- Sirve como la fuente que Jarvis Chat cita cuando responde una pregunta (`SPEC_JARVIS.md` §6.6) —
  toda cita de fuente en el chat debe poder rastrearse hasta una entrada de este timeline.

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| Un evento del timeline no generó ninguna decisión/alerta (ej. digest sin actividad relevante) | Se muestra igual en el timeline como "sin novedades relevantes" — no desaparece, para que quede registro de que la sincronización sí corrió. |

## 3. REFERENCIA VISUAL

# [HU-006]: Jarvis Mode - Jarvis Chat conversacional multi-turno

## 1. CONTEXTO
| **Módulo:** Jarvis Chat / Command Center |
| :--- |

### **Como** usuaria **Quiero** hablarle a Jarvis en una conversación de ida y vuelta, con sesiones que tienen inicio y fin por tarea, en vez de llenar un formulario de una sola pregunta **Para** poder profundizar con preguntas de seguimiento sin repetir contexto y sin romper la ventana de contexto en tareas largas.

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. El chat vive en el panel persistente del Command Center (`SPEC_JARVIS.md` §2) — no es una
   pantalla separada a la que se navega.
2. La usuaria escribe en lenguaje natural; puede hacer preguntas de seguimiento
   ("¿y qué falta de eso?") sin repetir el contexto ya dado en el mismo hilo.
3. Al iniciar una tarea concreta ("crear las HUs de X"), el sistema abre una **sesión con
   propósito explícito**; al cerrarla (o alcanzar el límite de contexto), ofrece continuar en una
   **nueva versión** de la misma sesión (v2, v3...) en vez de perder el hilo o romper silenciosamente.
4. Cualquier consecuencia de la conversación (alerta resuelta, gap cerrado, proyecto actualizado)
   se refleja **al instante** en el Panel de Estado de la misma pantalla.
5. El historial de sesiones cerradas queda consultable ("¿qué decidimos la vez que armamos las
   HUs de X?") — cerrar no es borrar.

### 2.2. Casos de Uso y Reglas de Negocio
- `POST /jarvis/chat` acepta `{conversationId?, message}` — sin `conversationId`, crea sesión
  nueva con `purpose` obligatorio.
- Dentro de un turno, Jarvis puede invocar herramientas antes de responder (loop agéntico, no una
  sola llamada a Claude): `readProjectBrain`, `readTimeline`, `readReconciliation`, `invokeAgent`,
  `writeMarMemory`.
- Cada afirmación cita su fuente (decisión/alerta/commit/HU/test); si falta información, lo dice
  explícitamente — nunca inventa avance.
- Una pregunta sin proyecto explícito ("¿qué está bloqueado esta semana?") se resuelve cruzando
  todos los proyectos activos, no solo el último abierto.
- Si la pregunta nombra un proyecto ambiguo (coincide parcialmente con más de uno), Jarvis
  pregunta de vuelta para desambiguar antes de responder.

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| La sesión se acerca al límite de la ventana de contexto | Se corta y abre automáticamente una nueva versión (v2) del mismo propósito, con un resumen de lo relevante de la versión anterior — no se trunca en silencio ni se pierde la tarea a medias. |
| La pregunta requiere datos de un proyecto sin Brain (recién creado, sin repos ni actas) | Jarvis responde explícitamente que no hay información suficiente para ese proyecto — no inventa un estado. |
| Se invoca una herramienta (ej. `invokeAgent`) y esta falla (401, timeout) | El error se muestra en el chat de forma legible ("no pude invocar a Gabi: [motivo]"), no como un JSON crudo ni un fallo silencioso. |

## 3. REFERENCIA VISUAL
> Panel de Chat del Command Center, `SPEC_JARVIS.md` §2. `[Pendiente: Definir en Tech Ref]`.

# [HU-007]: Jarvis Mode - Memoria de Mar (glosario vivo del sistema)

## 1. CONTEXTO
| **Módulo:** Memoria de Mar |
| :--- |

### **Como** usuaria **Quiero** que Jarvis recuerde entre conversaciones qué ya entiendo del sistema, qué me falta decidir, y las correcciones que hago sobre cómo me entendió **Para** no tener que repetirle contexto sobre mí misma cada vez que abro una conversación nueva.

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. Drill-down propio "Memoria de Mar" — lista de entradas tipo glosario vivo, ej. *"Jarvis = mini
   me = Orquestrador 360, mismo sistema"*.
2. Cada entrada es editable manualmente — la usuaria puede corregir algo que Jarvis asumió mal,
   igual que se corrige una memoria mal guardada.
3. Durante el chat, cuando la usuaria confirma o corrige algo sobre el sistema mismo (no sobre un
   proyecto puntual) — ej. "ok, entendido, no hace falta que me lo repitas" — Jarvis lo guarda
   aquí automáticamente, visible de inmediato en este drill-down.
4. Toda conversación nueva carga esta memoria como contexto — la usuaria no repite quién es ni
   qué ya sabe.

### 2.2. Casos de Uso y Reglas de Negocio
- Es un store separado de cada Project Brain (`GET/POST /mar/memory`) — vive a nivel sistema, no
  por proyecto.
- Tipos de entrada: `understanding` (algo que Mar ya entiende), `open_question` (pendiente de
  decidir), `correction` (una corrección explícita sobre una asunción previa de Jarvis).
- Fuente de cada entrada: `chat` (generada durante una conversación) o `manual` (editada
  directamente en el drill-down).

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| Jarvis intenta escribir una entrada duplicada (misma idea ya registrada) | No se duplica — se actualiza la entrada existente con la fecha más reciente, en vez de acumular repetidos. |
| La usuaria borra una entrada que el chat sigue citando en una sesión abierta | La sesión abierta mantiene su propia copia del contexto ya cargado (no cambia retroactivamente); la próxima sesión nueva ya no la incluye. |

## 3. REFERENCIA VISUAL

# [HU-008]: Jarvis Mode - Autoevaluación multidimensional y continua

## 1. CONTEXTO
| **Módulo:** Autoevaluación / Calidad de Agentes |
| :--- |

### **Como** usuaria **Quiero** que cada output de agente se evalúe en varias dimensiones concretas (eficiencia, acertividad, formato, calidad) inmediatamente después de producirse **Para** tener feedback disponible al momento, no solo como una tendencia que se nota semanas después.

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. En el panel "Estado de Agentes" (ya existente), cada agente muestra sus 4 dimensiones más
   recientes (no un único score genérico): Eficiencia, Acertividad, Formato, Calidad.
2. Inmediatamente después de invocar un agente (desde el chat o desde "Invocar Agente"), el
   resultado de las 4 dimensiones aparece junto al output — sin esperar ningún job posterior.
3. Si alguna dimensión cae por debajo del umbral en 2 invocaciones seguidas del mismo agente, se
   genera una propuesta de ajuste de prompt, visible como `open_question` en la Memoria de Mar —
   nunca autoaplicada, siempre pendiente de aprobación de Mar.

### 2.2. Casos de Uso y Reglas de Negocio
- Dimensiones: **Eficiencia** (resuelve lo pedido sin pasos/contexto de más), **Acertividad**
  (correcto/relevante respecto a lo preguntado), **Formato** (respeta el contrato esperado — JSON
  estricto, estructura de HU, etc.), **Calidad general** (rúbrica ya existente de
  `AgentEvaluator`: completeness, clarity, adherence, actionability, alignment — se mantiene como
  quinta dimensión, no se reemplaza).
- Cada dimensión se acumula en su propia serie de tiempo (no un promedio único que oculte cuál de
  las 4 es la que está fallando).
- Umbral decidido: **2 invocaciones seguidas** por debajo del umbral en una misma dimensión
  disparan la propuesta — no una sola caída puntual (que puede ser ruido).

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| El agente invocado no tiene rúbrica propia (agentes spec-kit sin evaluador dedicado) | Cae a la rúbrica genérica ya existente en `AgentEvaluator` — no falla la evaluación por falta de rúbrica específica. |
| Dos invocaciones bajas no son consecutivas (hay una buena en medio) | No dispara la propuesta de ajuste — el criterio es estrictamente "2 seguidas", no "2 de las últimas N". |

## 3. REFERENCIA VISUAL
> Panel "Estado de Agentes" (ya existente en el dashboard), con las 4 dimensiones agregadas.
> `[Pendiente: Definir en Tech Ref]` para el mockup actualizado.

# [HU-009]: Jarvis Mode - Changelog de mejoras del sistema

## 1. CONTEXTO
| **Módulo:** Autoevaluación / Analítica |
| :--- |

### **Como** usuaria **Quiero** un changelog de los ajustes que se le hicieron al sistema (qué se cambió, por qué, y qué pasó con las métricas después) **Para** tener evidencia concreta de que el sistema mejora con el tiempo, no solo la palabra de que mejoró.

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. Dentro de "Analítica completa" (drill-down), una sección "Changelog de mejoras": lista
   cronológica de ajustes aplicados a agentes (ej. cambios de prompt aprobados desde HU-008), con
   fecha, motivo, y el score de cada una de las 4 dimensiones antes/después del ajuste.
2. Cada entrada del changelog es clickeable y lleva al detalle de las invocaciones que motivaron
   el ajuste (drill-down al evento crudo, no solo el resumen).

### 2.2. Casos de Uso y Reglas de Negocio
- Solo se registran ajustes que Mar **aprobó explícitamente** (nunca autoaplicados) — el
  changelog es de cambios reales, no de propuestas descartadas.
- El "antes/después" de cada entrada usa la misma ventana de tiempo para ambos lados (ej. 2
  semanas antes vs. 2 semanas después) para que la comparación sea justa.

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |

# [HU-010]: Jarvis Mode - Panel de Analítica de negocio

## 1. CONTEXTO
| **Módulo:** Analítica |
| :--- |

### **Como** usuaria **Quiero** un panel de números concretos y priorizados (uso, calidad, reconciliación, costo) con capacidad de drill-down a los eventos crudos **Para** tener evidencia auditable de que el sistema es real y que mejora, respondiendo a la retroalimentación de que "no hay números que lo demuestren".

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)
1. Drill-down "Analítica completa", organizado por la prioridad ya definida en `SPEC_JARVIS.md`
   §7 (P0 primero, visualmente más prominente; P1-P3 debajo).
2. **P0**: número de outputs por tipo (HUs, specs, planes, actas, evaluaciones, reconciliaciones),
   número de usos (invocaciones totales por agente/proyecto/semana), gaps de reconciliación
   encontrados vs. cerrados.
3. **P1**: tasa de aceptación por tipo de output, calidad en el tiempo (4 dimensiones por agente,
   serie), costo por output (tokens/USD reales).
4. **P2**: comparación antes/después, tendencia semana a semana, distribución por proyecto/cliente.
5. **P3**: tiempo ahorrado estimado (marcado explícitamente como aproximado).
6. Cada número tiene un control de drill-down que lleva a los eventos crudos que lo componen — sin
   excepción, sin números "de fe".
7. Sección aparte de **monitoreo de costos de infraestructura** (Vercel, Upstash, Anthropic total
   de cuenta) con alertas si algún proveedor sale de su free tier o supera un umbral definido —
   mismo canal de alerta que el resto del Brain (chat + Panel de Estado), no un email aparte.

### 2.2. Casos de Uso y Reglas de Negocio
- "Tiempo ahorrado estimado" siempre se etiqueta visualmente como aproximado — nunca se presenta
  con la misma certeza que un número medido (ej. costo real en tokens).
- Las métricas P0 deben poder mostrarse incluso con poco histórico (desde el primer día de uso);
  las P2/P3 pueden mostrar "insuficiente historial todavía" mientras se acumulan datos — no se
  inventa una tendencia con un solo punto de dato.

### 2.3. Manejo de Errores
| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| Se pide drill-down de una métrica y el evento crudo ya no existe (fue purgado) | Se muestra explícitamente "evento no disponible" — nunca se sintetiza un evento falso para completar el drill-down. |
| El proveedor de costos (Vercel/Upstash/Anthropic) no responde al consultar el gasto actual | La alerta de costos se marca como "no verificado desde [hora]" — no asume que el gasto es cero ni oculta que falló la consulta. |
