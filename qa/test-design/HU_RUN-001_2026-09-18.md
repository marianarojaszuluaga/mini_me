# [HU-007]: Test Consolidator - Notificación de Reporte de Testing Manual vía Google Chat

## 1. CONTEXTO
| **Módulo:** Agentes / Leo (Test Consolidator) |
| :--- |

### **Como** Project Delivery Manager **Quiero** consolidar los resultados de un testeo manual ejecutado sobre casos diseñados por Cata y publicar el reporte en Google Chat **Para** tener visibilidad inmediata del estado de calidad sin salir del canal de comunicación del equipo

---

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)

1. El sistema expone el endpoint `POST /agents/leo/notify` que acepta un body JSON con los campos:
   - `input` (string, requerido): texto o estructura con los resultados del testeo manual a consolidar.
   - `context` (object, requerido): contexto del proyecto / corrida de testing.
   - `webhookUrl` (string, requerido): URL del webhook entrante de Google Chat al que se publicará el mensaje.

2. Al recibir una request válida, el endpoint:
   1. Ejecuta el agente Leo con `input` y `context`.
   2. Parsea el output JSON de Leo, extrayendo los campos `report` y `chat_message`.
   3. Llama a `app/services/google_chat_client.py::send_message` con `chat_message` y `webhookUrl`.
   4. Publica el mensaje en el espacio de Google Chat asociado al webhook.

3. El campo `report` contiene las estadísticas consolidadas del testeo (ej. total de casos, passed, failed, bloqueados).
4. El campo `chat_message` contiene el texto formateado listo para publicar en Google Chat.
5. La respuesta del endpoint refleja éxito cuando Google Chat devuelve HTTP 200.

### 2.2. Casos de Uso y Reglas de Negocio

- **Origen del webhook:** La `webhookUrl` es generada por un administrador del espacio de Google Chat en *Configuración del espacio > Apps e integraciones > Agregar webhook*. No requiere OAuth ni Auth Profile.
- **Autenticación:** El endpoint no requiere integración OAuth. La autorización la otorga implícitamente la URL del webhook.
- **Parseo de output:** El sistema espera que el output de Leo sea JSON válido con exactamente los campos `report` y `chat_message`. Si el parseo falla, el endpoint devuelve error (ver sección 2.3).
- **Responsabilidad del agente Leo:** Leo genera el reporte estadístico a partir del input recibido; la lógica de consolidación reside en el agente, no en el endpoint.
- **Casos diseñados por Cata:** Los casos de testing que se consolidan son los producidos por el agente Cata (test designer). El endpoint no valida su origen; recibe el resultado ya ejecutado manualmente por un humano.

### 2.3. Manejo de Errores

| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| `webhookUrl` ausente | El endpoint SÍ corre a Leo igual (genera el reporte), pero responde HTTP 200 con `chatNotification: {sent: false, reason: "No webhookUrl provided..."}` — NUNCA rechaza la request. |
| `webhookUrl` inválida (no es una URL real de chat.googleapis.com) | Leo corre igual, `send_message` lanza `GoogleChatError`, capturado por el endpoint — responde HTTP 200 con `chatNotification: {sent: false, reason: "..."}`. |
| Google Chat devuelve error HTTP real (ej. 403, 500) | Mismo patrón: HTTP 200 en la respuesta del endpoint, con `chatNotification.sent: false` y el motivo real de Chat en `reason`. El endpoint nunca fabrica éxito. |
| Output de Leo no es JSON válido o le falta `chat_message` | El endpoint responde igual HTTP 200 con `chatNotification: {sent: false, reason: "leo's output had no parseable chat_message field."}` — el `report` generado (si lo hay) sigue disponible en la respuesta. |

**Corrección 2026-09-18 (verificado contra `app/routers/agents.py::leo_notify`)**: el endpoint **nunca devuelve un código de error HTTP por un problema del lado del webhook/Chat** — siempre responde 200, y el éxito/fallo del envío se lee en el campo `chatNotification` del body. Esto es intencional: la generación del reporte de Leo y el intento de notificación son dos cosas separadas, y una falla en la segunda no debe ocultar el resultado de la primera.

# [HU-008]: mia (Meeting Messenger) - Ingesta y entrega 
de transcripciones de reunión vía Google Drive

## 1. CONTEXTO

| **Módulo:** Agente mia — Meeting Messenger |
| :--- |

### **Como** Project Delivery Manager
**Quiero** que `mia` recupere automáticamente la transcripción 
de una reunión desde Google Drive y, una vez que `santi` 
genere el acta, la deposite de vuelta en Drive y en el 
Project Brain
**Para** que el flujo de generación de actas sea continuo 
y no requiera intervención manual en la transferencia 
de archivos

---

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)

**Paso 1 — Activación de mia (pre-santi)**

- El usuario indica a `mia` que hay una reunión lista para 
  procesar (puede ser por nombre de archivo, carpeta o 
  instrucción en lenguaje natural).
- `mia` invoca `list_files_in_folder(folder_id)` sobre la 
  carpeta configurada en Drive para listar los archivos 
  disponibles.
- Si hay más de un archivo candidato, `mia` presenta la 
  lista y solicita confirmación al usuario antes de 
  continuar ("¿Proceso el archivo 'Reunión equipo 
  2026-02-04.txt'?").
- `mia` invoca `get_file_text(file_id)` para obtener el 
  texto de la transcripción o nota de reunión.
- `mia` entrega el texto extraído a `santi` como input 
  estructurado, indicando título del archivo y fecha de 
  creación en Drive como metadatos de contexto.

**Paso 2 — Entrega post-santi**

- Una vez que `santi` devuelve el acta generada (texto 
  completo en Markdown), `mia` sube el documento a Drive:
  - Carpeta de destino: `[Pendiente: Definir carpeta 
    de destino en configuración del proyecto]`
  - Nombre del archivo: `Acta_[nombre_reunión_original]
    _[YYYY-MM-DD].md`
- `mia` actualiza el **Project Brain** con el acta: 
  añade una entrada en la sección correspondiente al 
  módulo/proyecto con fecha, título de reunión y 
  texto del acta.
- `mia` confirma al usuario: "✅ Acta subida a Drive y 
  registrada en el Project Brain."

---

### 2.2. Casos de Uso y Reglas de Negocio

**RN-01 — Scope OAuth requerido**

- La cuenta de Google de la usuaria **debe estar conectada 
  con los scopes `drive.readonly` + `drive.file`**.
- Si el token almacenado fue generado con un scope anterior 
  (solo `drive.readonly` o menor), Google retornará `403 
  Forbidden` en cualquier operación de escritura.
- **Este es un paso de configuración manual real, no un 
  bug del sistema:** la usuaria debe revocar el token viejo 
  y completar el flujo OAuth nuevamente para obtener un 
  token con los scopes ampliados.
- El sistema no puede autorregenerarse el token: requiere 
  intervención humana explícita (ver sección 2.3, 
  escenario E-03).

**RN-02 — Unicidad del archivo de acta en Drive**

- Si ya existe un archivo con el mismo nombre en la carpeta 
  de destino, `mia` debe crear una nueva versión con sufijo 
  `_v2`, `_v3`, etc., sin sobreescribir.

**RN-03 — Formato de entrada aceptado**

- `mia` procesa archivos de texto plano (`.txt`, `.md`) y 
  documentos de Google Docs exportables como texto.
- Archivos de audio, video o formatos binarios no son 
  soportados en esta HU: `[Pendiente: Definir soporte 
  de transcripción automática en HU futura]`

**RN-04 — Atomicidad del flujo**

- Si `santi` falla o no devuelve acta, `mia` **no debe** 
  intentar subir nada a Drive ni actualizar el Project 
  Brain. El flujo se cancela y se notifica al usuario.

**RN-05 — Identificación de carpeta de origen**

- La carpeta de Drive de donde `mia` lee transcripciones 
  debe estar definida en la configuración del proyecto 
  (`folder_id`). No se navega Drive de forma abierta.
  `[Pendiente: Definir variable de entorno o config 
  FOLDER_ID_TRANSCRIPCIONES]`

---

### 2.3. Manejo de Errores

| Escenario | Mensaje / Acción |
| :--- | :--- |
| **E-01** — No se encuentran archivos en la carpeta de origen | `mia` informa: "No encontré archivos en la carpeta configurada de Drive. Verificá que la transcripción esté subida y que el `folder_id` sea correcto." Flujo se detiene. |
| **E-02** — `get_file_text` retorna texto vacío o nulo | `mia` informa: "El archivo existe pero no pude extraer texto. Puede ser un formato no soportado o un documento vacío." Solicita al usuario confirmar o elegir otro archivo. |
| **E-03** — Error 403 al subir el acta a Drive (token sin scope `drive.file`) | `mia` informa: "⚠️ No tengo permiso para escribir en Drive. Tu cuenta de Google necesita reconectarse con permisos ampliados (drive.file). Por favor, revocá el token anterior y completá el flujo de autenticación nuevamente." Provee el link o comando para iniciar el flujo OAuth. Flujo de escritura se cancela; el acta se entrega igualmente al usuario en texto para que la suba manualmente si lo necesita. |
| **E-04** — Error 403 al leer (token sin scope `drive.readonly`) | Igual que E-03, indicando que el problema afecta también la lectura. |
| **E-05** — `santi` falla o no retorna acta | `mia` informa: "santi no pudo generar el acta. No se realizaron cambios en Drive ni en el Project Brain." Flujo se cancela. |

| :--- |

### **Como** sistema de sincronización automatizado (nico) **Quiero** revisar diariamente las carpetas estándar del repositorio del proyecto y subir los archivos finalizados a sus carpetas homólogas en Google Drive como Google Docs reales **Para** mantener una copia actualizada y legible en Drive sin interferir ni sobreescribir el contenido existente en esa plataforma

---

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)

1. El agente `nico` se ejecuta **una vez por día** de forma programada (trigger: schedule diario, hora a definir en configuración del proyecto).
2. Al ejecutarse, `nico` recorre en orden las **6 carpetas estándar** del repositorio conectado al proyecto:
   - `01-Planning`
   - `02-UX UI`
   - `03-Development`
   - `04-QA`
   - `05-Deliveries`
   - `06-FollowUp`
   > Estas carpetas son creadas por el scaffold de onboarding del proyecto. Si alguna no existe en el repo al momento de la ejecución, `nico` la omite sin error y continúa con las siguientes.
3. Por cada carpeta, `nico` identifica los **archivos marcados como finalizados** [Pendiente: Definir criterio de "finalizado" — flag en metadata del archivo, nombre de rama, campo en frontmatter `.md`, o estado en sistema externo].
4. Por cada archivo finalizado detectado, `nico` llama al método existente:
   ```
   app/services/google_drive_client.py :: create_doc
   ```
   pasando el contenido del archivo y la carpeta de destino correspondiente en Google Drive.
5. El archivo se crea en Drive como **Google Doc real** (no se sube como attachment `.md` ni como archivo plano).
6. La carpeta de destino en Drive es la **homóloga** a la carpeta de origen en el repo:
   | Carpeta Repo | Carpeta Drive |
   | :--- | :--- |
   | `01-Planning` | `01-Planning` (en Drive del proyecto) |
   | `02-UX UI` | `02-UX UI` (en Drive del proyecto) |
   | `03-Development` | `03-Development` (en Drive del proyecto) |
   | `04-QA` | `04-QA` (en Drive del proyecto) |
   | `05-Deliveries` | `05-Deliveries` (en Drive del proyecto) |
   | `06-FollowUp` | `06-FollowUp` (en Drive del proyecto) |
7. Si un archivo ya existe como Google Doc en la carpeta homóloga de Drive, `nico` **crea una nueva versión del documento** (update) sin tocar ningún otro contenido de esa carpeta [Pendiente: Confirmar si `create_doc` ya maneja upsert por nombre/ID o si se requiere lógica adicional de detección de duplicados].
8. Al finalizar la corrida diaria, `nico` genera un **log de ejecución** con: fecha, archivos procesados, archivos omitidos y resultado por archivo (éxito / error).

---

### 2.2. Casos de Uso y Reglas de Negocio

#### RN-001 — Flujo estrictamente unidireccional (CRÍTICO)
- `nico` **SOLO envía información desde el repositorio hacia Google Drive**.
- `nico` **nunca lee, descarga, modifica ni borra contenido** que ya exista en Drive.
- Las carpetas de Drive pueden contener archivos adicionales creados por otras personas o procesos. `nico` los ignora completamente.
- Esta regla no tiene excepciones. Cualquier operación de lectura desde Drive debe ser bloqueada a nivel de implementación.

#### RN-002 — Scope de archivos a sincronizar
- Solo se procesan archivos ubicados en las 6 carpetas estándar listadas.
- No se procesan subcarpetas anidadas [Pendiente: Confirmar si el sync es recursivo o solo primer nivel].
- Solo se suben archivos con estado "finalizado" [Pendiente: Definir criterio formal de "finalizado"].

#### RN-003 — Integridad del contenido existente en Drive
- Si la carpeta homóloga en Drive no existe, `nico` la crea antes de subir el archivo.
- Si la carpeta homóloga existe y tiene contenido propio, `nico` no la modifica, no la reorganiza y no elimina ningún archivo de ella.

#### RN-004 — Autenticación con Google
- `nico` comparte el mismo pendiente de reconexión de cuenta de Google que el agente `mia` (referencia: HU-008).
- Hasta que la reconexión de cuenta Google esté resuelta, este flujo **no puede ejecutarse en producción**.

# [HU-010]: Auth / OAuth — Ampliación de Scopes de Google OAuth (Drive)

## 1. CONTEXTO

| **Módulo:** Auth — OAuth Google (`app/routers/oauth.py`) |
| :--- |

### **Como** sistema (agente Mia / Nico) **Quiero** solicitar al usuario los permisos `drive.readonly` y `drive.file` durante el flujo de autenticación OAuth de Google **Para** poder leer y escribir archivos en Google Drive en nombre del usuario autenticado

---

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)

1. Cuando una usuaria/o inicia el flujo de conexión de cuenta Google (nuevo registro o reconexión), el sistema redirige a Google OAuth con los siguientes scopes declarados:
   - `openid`
   - `email`
   - `profile`
   - `https://www.googleapis.com/auth/drive.readonly`
   - `https://www.googleapis.com/auth/drive.file`
2. Google muestra la pantalla de consentimiento listando explícitamente los permisos de Drive solicitados.
3. La usuaria/o otorga el consentimiento y es redirigida/o de vuelta a la aplicación.
4. El token de acceso resultante incluye los nuevos scopes de Drive.
5. El sistema almacena el token (access token + refresh token) asociado al Auth Profile de Google del usuario.

### 2.2. Casos de Uso y Reglas de Negocio

- **RN-01:** El cambio de scopes ya está implementado en `app/routers/oauth.py`. Esta HU documenta el comportamiento esperado post-implementación; no requiere nuevo desarrollo de backend para el scope request.
- **RN-02:** Los scopes `drive.readonly` y `drive.file` son **acumulativos** sobre los scopes previos (`openid email profile`). No reemplazan los anteriores.
- **RN-03:** El parámetro `access_type=offline` debe estar presente en el request OAuth para garantizar la emisión de un `refresh_token` (requerido para operaciones de larga duración de los agentes).
- **RN-04:** El parámetro `prompt=consent` debe evaluarse: si el usuario ya había otorgado consentimiento con el scope viejo, Google puede no re-mostrar la pantalla sin este parámetro. [Pendiente: Definir en Tech Ref si se fuerza `prompt=consent` en reconexión].
- **RN-05:** Solo afecta conexiones Google. Otros proveedores OAuth no se ven afectados.

### 2.3. Manejo de Errores

| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| La usuaria/o rechaza los permisos de Drive en la pantalla de consentimiento de Google | El sistema cancela el flujo y muestra: `"Para usar esta funcionalidad necesitás otorgar permisos de Google Drive. Podés intentarlo nuevamente."` |
| Google devuelve error en el callback OAuth (`error` param presente en redirect) | El sistema registra el error en logs y redirige al usuario con mensaje: `"Hubo un problema al conectar tu cuenta de Google. Intentá de nuevo."` |
| El token recibido no contiene los scopes de Drive (verificación post-auth) | El sistema registra advertencia en logs. [Pendiente: Definir si bloquea o permite acceso parcial — definir en Tech Ref] |
| Timeout durante el redirect de Google | El sistema muestra: `"La conexión tardó demasiado. Revisá tu conexión e intentá de nuevo."` |

# [HU-011]: Auth / OAuth — Reconexión Manual de Cuentas Google Existentes para Obtener Scopes de Drive

## 1. CONTEXTO

| **Módulo:** Auth — OAuth Google / Gestión de Auth Profiles |
| :--- |

### **Como** usuaria/o con una cuenta de Google conectada **antes** de la ampliación de scopes **Quiero** poder reconectar mi cuenta de Google repitiendo el flujo OAuth **Para** que mi token de acceso incluya los nuevos permisos de Drive y los agentes Mia y Nico puedan operar correctamente

---

## 2. CRITERIOS DE ACEPTACIÓN (AC)

### 2.1. Interfaz y Experiencia (Happy Path)

1. La usuaria/o accede a la sección de gestión de cuentas conectadas / Auth Profiles en la aplicación. [Pendiente: Definir ruta/pantalla exacta en Tech Ref]
2. El sistema identifica que el Auth Profile de Google existente fue conectado con el scope viejo (sin Drive). [Pendiente: Definir en Tech Ref el mecanismo de detección — ej. campo `scopes` almacenado en DB vs. introspección del token].
3. El sistema muestra un **aviso visible** al usuario indicando que su cuenta de Google necesita reconexión para habilitar las funcionalidades de Drive:
   - Texto sugerido: `"Tu cuenta de Google necesita permisos adicionales para que los agentes puedan acceder a Drive. Reconectá tu cuenta para continuar."`
4. La usuaria/o hace clic en el CTA de reconexión (ej. botón `"Reconectar cuenta de Google"`).
5. El sistema inicia el flujo OAuth de Google con los scopes completos (incluyendo `drive.readonly` y `drive.file`), tal como define **HU-010**.
6. La usuaria/o completa el consentimiento en Google.
7. El sistema reemplaza el token viejo almacenado en el Auth Profile por el nuevo token con scopes de Drive.
8. El sistema confirma la reconexión exitosa con feedback visual: `"¡Tu cuenta de Google fue reconectada correctamente!"` [Pendiente: Definir componente UI — toast, banner, modal].

### 2.2. Casos de Uso y Reglas de Negocio

- **RN-01:** Este es un proceso **manual y voluntario**. El sistema **no migra ni actualiza tokens automáticamente**. Cada usuaria/o debe iniciar la reconexión por su cuenta.
- **RN-02:** Los Auth Profiles de Google creados **después** de la implementación de HU-010 ya tendrán los scopes correctos y **no requieren reconexión**.
- **RN-03:** Los Auth Profiles de Google creados **antes** del cambio de scopes conservan su token viejo hasta que el usuario reconecte manualmente. Durante ese período, las funcionalidades que requieran Drive no estarán disponibles para esos usuarios.
- **RN-04:** La reconexión **sobreescribe** el access token y refresh token existentes en el Auth Profile. No se crea un nuevo perfil duplicado.
- **RN-05:** Si la usuaria/o cancela el flujo de reconexión sin completarlo, el token viejo permanece sin cambios. No se pierde el acceso anterior.
- **RN-06:** [Pendiente: Definir en Tech Ref si se implementa un indicador de estado en el Auth Profile — ej. campo `scopes_version` o `requires_reconnect: bool` — para poder detectar y notificar a usuarios afectados de forma consistente].
- **RN-07:** El agente orquestador (Mia / Nico) que intente operar sobre Drive con un token sin los scopes necesarios debe manejar el error de permisos de Google y notificar al usuario que debe reconectar. [Pendiente: Definir flujo de error en agentes — relacionar con HUs de Mia/Nico].

### 2.3. Manejo de Errores

| Escenario | Mensaje de Error / Acción |
| :--- | :--- |
| La usuaria/o completa el flujo OAuth pero Google no emite los scopes de Drive (ej. volvió a rechazarlos) | El sistema no actualiza el token. Muestra: `"No se obtuvieron los permisos necesarios. Para usar Drive, reconectá tu cuenta y aceptá todos los permisos solicitados."` |
| Error en el callback OAuth durante la reconexión | El token viejo no se sobreescribe. El sistema muestra: `"Hubo un error al reconectar tu cuenta. Tu conexión anterior sigue activa. Intentá de nuevo."` |
